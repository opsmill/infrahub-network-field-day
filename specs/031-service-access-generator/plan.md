# Implementation Plan: Application Access Grant Generator

**Branch**: `031-service-access-generator` | **Date**: 2026-09-16 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/031-service-access-generator/spec.md`

## Summary

`ServiceAppAccess` is the one service kind that produces nothing: schema, a menu entry and six contract tests, but no generator, no transform, no artifact and no seed object. This cycle adds `generate-app-access`, which turns an approved grant into the firewall objects that permit the session — an address-book entry for the destination VIP, a service object per permitted port, and a `SecurityPolicyRule` joining them — and links them back through `granted_rules`.

Nothing downstream needs changing. `transforms/junos_config.gql` queries `SecurityGenericAddress` and `SecurityPolicy` unfiltered, so generated objects are rendered by the existing artifact, and the deployment reconciler pushes it onto `fw1`. Withdrawal is the SDK's tracking context, which `generate-fabric-peering` already relies on.

Phase 0 resolved the two design questions the spec deferred and corrected one premise in it: the destination zone is derived through `IpamVRF`, not through firewall-interface containment, because the handoff interfaces are `/30` point-to-points that contain nothing but the handoff. See [research.md](./research.md) R2.

## Technical Context

**Language/Version**: Python >=3.11,<3.14 (constitution: Technology Stack)

**Primary Dependencies**: `infrahub-sdk[all]>=1.19.0` (`InfrahubGenerator`, tracking context), Infrahub 1.10.6

**Storage**: Infrahub graph (Neo4j). No new schema — see SC-008.

**Testing**: pytest with pytest-asyncio; `tests/unit/test_app_access_generator.py` new; `tests/unit/test_junos_config.py` must keep passing unchanged

**Target Platform**: Infrahub generator, executed by `infrahubctl generator`, in proposed changes, and after merge

**Project Type**: Infrahub repository artifact — generator, per the `infrahub-speckit` routing for this cycle

**Performance Goals**: Not applicable at lab scale. One grant produces at most one rule, one address entry and N service objects for N ports.

**Constraints**:
- Junos is first-match within a zone pair, so a generated rule must never sort above the `deny-spoofed-infra` baseline at `index: 10`
- `junos_config.py::_addresses` skips any address with no `book_index`, so a generated entry without one is silently absent from the rendered book
- `tests/unit/test_junos_config.py` holds the artifact byte-for-byte against `junos.conf`, including `test_the_exclusions_add_up`
- The generator must raise before writing anything on an incomplete model, because a partial write is the one path by which the tracking context deletes a real object

**Scale/Scope**: One new generator, one `.gql`, one generated query module, one group, one seed object, one test module. Six existing files touched.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Gate | Status |
| --- | --- | --- |
| **I. Schema-Driven Architecture** | No code may reference undefined schema elements | **PASS.** Every field this generator reads or writes exists today. `managed_by_service`, `granted_rules`, `book_index` and `log_session_close` were added by cycles 023–026 for exactly this generator and have no writer yet. SC-008 asserts no file under `schemas/` changes. No protocol regeneration needed. |
| **II. Idempotent Operations** | `allow_upsert=True`; explicit natural key; repeated-run validation defined | **PASS.** All saves use `allow_upsert=True`. Natural keys are the HFIDs already on these kinds (`name__value` on `SecurityGenericAddress`, `SecurityService`, `SecurityPolicyRule`). Names are derived deterministically from the grant name (research R3), so a second run upserts the same nodes. Repeated-run validation is FR-071 plus `$infrahub-test-generator-idempotence`. |
| **III. Type Safety** | Typed models for all GraphQL responses; mypy `disallow_untyped_defs` | **PASS.** `generate_app_access_query.py` is generated by `infrahubctl graphql generate-return-types` and used in the generator; FR-014 forbids hand-writing it. |
| **IV. Test-Required Quality** | Unit tests exist; all linters pass; C901 ≤ 17 | **PASS with a note.** Unit tests are FR-070 to FR-073. The derivation, index allocation and validation logic are split into named helpers rather than one `generate()` body, to stay under the complexity limit. Integration coverage is `$infrahub-run-integration-tests`; idempotence is `$infrahub-test-generator-idempotence`. |
| **V. Convention-Based Structure** | `generate_<entity>.py` with matching `.gql`; numbered object files | **PASS with one documented deviation.** The constitution says `generate_<entity>.py` with `<entity>_generator_query.py`. Every generator in this repository actually uses `generate_<entity>_query.py` (`generate_fabric_peering_query.py`) or `<entity>_generator_query.py` (`fabric_generator_query.py`) — both spellings are present. This plan follows `generate_fabric_peering`, the nearest neighbour and the only other service generator. Recorded in Complexity Tracking. |

**Deployment-state rule** (`AGENTS.md`): this generator does not read, write, target or trigger from `DeploymentState` or `DeploymentDiffFile`. `tests/unit/test_deployment_schema_contract.py` is unaffected.

**Service-layer dependency rule**: the dependency runs one way — service files name technical kinds, technical files name no service kind. This generator reads a service and writes technical objects, which is the sanctioned direction. `tests/unit/test_service_layer_schema_contract.py` is unaffected because no schema changes.

**Post-Phase 1 re-check**: PASS. The design adds no schema, no dependency, and no file outside the conventions above. Complexity Tracking carries one naming deviation and nothing else.
